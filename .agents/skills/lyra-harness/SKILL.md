# Lyra Cloud Swarm Harness Skill

This skill allows Antigravity to act as the primary local controller, dispatching heavy-lifting feature implementations to Lyra's autonomous agent runners in the cloud (AWS Bedrock) while retaining local oversight and permission control.

## Intelligent Workload Routing Decision Matrix

Before taking action, evaluate whether the task should run locally in Antigravity or dispatched to the Lyra Cloud Swarm:

| Task Type | Recommended Engine | Rationale |
| :--- | :--- | :--- |
| **Typo fix, single-file edit, documentation, quick shell check** | **Local Antigravity** | Instant response, 0 network latency, \$0.00 cloud cost. |
| **Multi-file feature architecture, domain services, database schemas** | **Lyra Cloud Swarm** | Decomposes architecture, runs parallel worktrees, automated peer review. |
| **Full test suite execution, heavy compilation, load testing** | **Lyra Cloud Swarm** | Offloads CPU, RAM, and battery drain to cloud runners. |
| **Security fuzzing & QA boundary validation** | **Lyra Cloud QA Sandbox** | Runs automated idempotency replay, overflow fuzzing, and auth checks. |

## Available MCP Tools (10 Standardized Tools)

Once the `lyra_harness` MCP server is loaded, Antigravity has access to:

### Swarm Orchestration
1. `lyra_dispatch_task(objective, workspacePath, model)`:
   - Initiates an autonomous Strands swarm on AWS Bedrock (default: `Claude Sonnet 4.6`).
   - Generates plan decomposition and parallel task worktrees.
2. `lyra_get_run_status(sessionId, runId)`:
   - Queries real-time execution state, active tasks, test checks, merge conflicts, and **FinOps token & dollar cost telemetry**.
3. `lyra_dispatch_and_pr(objective, workspacePath, repoOwner, repoName, branchName, title, body?, githubToken?)`:
   - 1-shot convenience tool: dispatches swarm, monitors tests and peer reviews, and automatically opens a GitHub Pull Request.

### Context & Permission Handshake
4. `lyra_get_pending_requests(runId)`:
   - Checks if remote cloud agents need specific local file context or elevated permissions.
5. `lyra_provide_file_context(requestId, content)`:
   - Sends local file snippets to the remote agent so the cloud swarm does not need full disk sync.
6. `lyra_respond_permission(requestId, approved, reason)`:
   - Grants or denies permission for sensitive actions (e.g. git pushes, external network access).

### Code Inspection & Merge Resolution
7. `lyra_inspect_diff(runId, filePath?)`:
   - Inspects the line-by-line unified diff and patch generated by Lyra cloud workers across isolated worktrees before merge or PR.
8. `lyra_resolve_conflict(runId, filePath, resolvedContent)`:
   - Resolves merge conflicts in a conflicting file from the local harness, updating the cloud worktree state cleanly.

### Dynamic QA & Pull Requests
9. `lyra_run_qa_sandbox(runId, targetUrl?, scenarios?)`:
   - Runs automated dynamic QA, fuzzing, and stress-testing ("Grok bot") for idempotency replays, boundary tests, and authorization checks.
10. `lyra_create_github_pr(repoOwner, repoName, branchName, title, body, githubToken)`:
    - Opens an official Pull Request on GitHub once tests and self-reviews pass.

## Automated Permission & Safety Policy

When handling permission requests (`lyra_respond_permission`):
- **Auto-Approve**:
  - Read-only queries to allowed workspace directories.
  - Safe test commands (`bun test`, `npm test`, `pytest`).
  - Creation of internal feature branches (`lyra/feat-*`).
- **Prompt User Before Approving**:
  - Pushing commits directly to `main` or production branches.
  - Provisioning billable persistent cloud resources (EC2, RDS).
  - Deleting files or dropping database schemas.
